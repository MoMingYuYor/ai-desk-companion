# 事务助手数据契约与验收细则

日期：2026-09-20。状态：设计文档，尚未实施。本文与 [技术设计与实施路线](技术设计与实施路线.md) 共同定义已确认的 R/O 全部任务及 F1、F2、F4、F6、F7、F8、F9、F11、F12；F12 最后实施。本文聚焦数据约束、迁移、接口执行语义和验收，不扩展功能范围。

## 1. 公共数据约定

实体 ID 使用不承载业务意义的字符串，主进程生成并校验；既有 ID 原样保留。所有可编辑业务实体使用整数 `revision`，初始值为 1，每次成功业务更新递增一次。`updated_at` 仅供显示和排序，不能替代并发控制。只读列表同时返回 revision，用户确认时提交所看到的值。

绝对执行时间、日志时间、提醒调度时间使用 UTC ISO 8601，并保留毫秒；既有日程的无时区本地时间保持原语义，通过集中转换函数进入调度。新周期规则额外保存 IANA 时区和本地墙钟时间。日期字段使用 `YYYY-MM-DD`，不能直接当作 UTC 午夜。持久化的 token 用量是可空非负整数；缺失不填零，金额缺少可靠价格来源时不计算。

普通日程查询采用半开区间 `[start, end)`，相邻时段不冲突。新全天日程使用本地日期的起始日与排他结束日；迁移需根据旧 `all_day` 和实际保存形式明确转换，使用既有全年合成数据检查显示天数，不对所有旧时间统一加一天。没有截止时间的待办不生成截止提醒。

业务写入、恢复、迁移和退出持久化统一通过主进程协调器，避免各模块自行关闭数据库或替换文件。数据库外的文件资源通过受控目录与清单维护，清理路径不能来自模型或任意 IPC 参数。

## 2. 核心数据字典与不变量

以下是目标数据模型。新增表在所属阶段实现时才进入实际 schema；本表不是已部署数据库清单。所有 JSON 字段都带明确结构版本并由运行时校验器解析，不能只依赖 TypeScript 类型断言。

| 数据对象 | 关键字段 | 唯一约束、索引与不变量 | 备份类别 |
| --- | --- | --- | --- |
| `operation_receipts` | operation_id、command、request_hash、result_ref、created_at | operation_id 唯一；同 ID 不同请求拒绝；结果与业务事务共同提交 | 业务，随所引用实体恢复 |
| `events` | 原字段、revision、deleted_at | ID 保留；有效区间；按状态、start_at、ID 查询；软删除不参与提醒 | 业务 |
| `todos` | 原字段、revision、parent_id、estimated_minutes、execution_status、status、deleted_at | execution_status 为 todo/doing/done；status 为 active/cancelled；取消与完成分别表达；按状态及 due_at 查询 | 业务 |
| `todo_time_blocks` | todo_id、event_id、created_at | `(todo_id,event_id)` 唯一；两端存在；删除关联不隐式删除共享事件 | 业务 |
| `action_candidates` | id、analysis_id、candidate_key、kind、payload、source_snapshot、status、revision | `(analysis_id,candidate_key)` 唯一；来源由程序绑定；状态 open/handled/dismissed | 业务 |
| `pending_items` | 原字段、candidate_id、resolution_ref、revision | 非空 candidate_id 唯一；旧手动条目 candidate_id 可空；结果与 handled 状态同时产生 | 业务 |
| `entity_changes` | id、operation_id、entity_ref、before_revision、after_revision、before_value、after_value、undone_by | 每个操作可有多条实体变更；撤销需全部必要实体仍匹配 after_revision | 业务，含敏感业务字段 |
| `recurrence_series` | id、parent_series_id、entity_kind、template、rule、timezone、start_local、until_local、count、revision | 首版 kind 为 event/todo；结束次数和日期不能互相矛盾；规则必须可在有限区间展开 | 业务 |
| `recurrence_instances` | logical_instance_id、series_id、occurrence_key、ordinal、entity_id、state、revision | logical_instance_id 主键；`(series_id,occurrence_key)` 唯一；取消及排除记录不能被重新物化 | 业务 |
| `recurrence_instance_keys` | series_id、occurrence_key、logical_instance_id | `(series_id,occurrence_key)` 唯一；系列拆分后旧键仍定位同一逻辑实例，不能复用为新事项 | 业务 |
| `recurrence_exceptions` | logical_instance_id、override、status、revision | 每逻辑实例最多一个有效例外；移动时间或拆分系列不改变所属逻辑实例 | 业务 |
| `reminder_jobs` | id、entity_ref、logical_instance_id、target_revision、rule_version、scheduled_at、snoozed_until、status、revision | 触发身份唯一；按 status、有效触发时间、ID 查询；取消任务不能再派发 | 业务，恢复后重新计算可执行状态 |
| `reminder_attempts` | job_id、attempt_no、started_at、finished_at、outcome、error_code | `(job_id,attempt_no)` 唯一；不记录令牌或原始异常中的正文 | 业务，旧记录可归档 |
| `analysis_request_snapshots` | id、manifest、content_hash、policy_version、created_at | manifest 保存精确材料/上下文引用、接收方地址和模型；引用不可变内容版本 | 业务审计，恢复后不能直接用于发送 |
| `analysis_runs` / `analysis_attempts` | id、snapshot_id、run_id、provider_id、model_id、status、started_at、duration_ms、usage | 每次尝试单独记录；runId 绑定会话；未知用量为 null | 业务审计 |
| `privacy_grants` | id、device_scope、snapshot_id 或入口策略、receiver_config_hash、expires_at、revoked_at | 活动授权本机有效；内容或接收方改变失效；过期和撤销不可继续发送 | 本机，不随业务备份恢复 |
| `providers` | 原字段、config_revision | 端点、模型能力或允许模型列表改变时递增；授权快照绑定修订；密钥保持单独加密字段 | 本机 |
| `mail_accounts` | 原字段、auth_type、transport、revision、lifecycle_epoch | 已验证邮箱身份与传输方式匹配；enabled 与同步状态分开；停用不可被 idle 回写重新启用 | 本机 |
| `gmail_remote_messages` | account_id、gmail_message_id、local_message_id、gmail_thread_id | `(account_id,gmail_message_id)` 唯一；local_message_id 连接既有邮件摘要 | 邮箱缓存，不进业务备份 |
| `gmail_sync_state` | account_id、history_id、oldest_day、page_checkpoint、initialized、lifecycle_epoch | history_id 保存字符串；先提交内容再推进同事务检查点；恢复业务不倒退远端游标 | 本机 |
| `gmail_attachment_refs` | local_attachment_id、gmail_message_id、gmail_attachment_id | 不借用 IMAP part 字段表达 Gmail ID；远端身份按账号校验 | 邮箱缓存 |
| `backup_catalog` / `backup_settings` | 归档 ID、受控路径、状态、创建时间、摘要；目录、频率、保留数量 | 临时或失败文件不计成功数量；只能清理本应用登记文件 | 本机 |

凭据不进入上述业务表的 JSON，也不进入 `operation_receipts`。操作回执记录允许展示的结果引用，不复制 API 请求全文或认证参数。业务变更记录可能包含事项标题、备注和来源，是用户数据，不属于可直接公开的诊断日志。

Gmail 接入需要对当前邮件表的 IMAP 专属非空字段进行显式迁移：账号的 host/port 对 gmail_api 可空、对 imap 必填；附件的 IMAP part 对 gmail_api 可空，并由独立 REST 引用表提供实际下载身份。正文结构字段采用带 transport 标签的可校验结构。不能填写虚假 host、port、UID 或 part 以绕过旧表约束。原 IMAP 行及其唯一约束保持有效，REST 的唯一身份由独立映射表约束；本地邮件 ID 仍为界面和分析来源共同使用的稳定 ID。

`todos.execution_status=done` 当且仅当 `completed_at` 非空；`status=cancelled` 时不派发提醒、不计入待办数量，但保留取消前执行状态供撤销。取消已完成事项不会擦除完成历史。删除使用软删除和关联约束，永久删除范围在界面明确列出；涉及多个实体的撤销必须整体校验，不能只恢复标题而留下错误关联。

## 3. 写入命令、幂等与持久化

共享契约按以下形状表达；这是拟实现接口，现有 API 接入时需同步修改主进程、preload、渲染层和测试，不能只添加类型文件。

```ts
type ErrorCode =
  | 'VALIDATION' | 'FORBIDDEN' | 'CONFLICT' | 'PERSIST_FAILED'
  | 'BACKUP_INVALID' | 'AUTH_REQUIRED' | 'NETWORK' | 'CANCELLED'
  | 'BUSY' | 'STALE_PREVIEW' | 'TARGET_UNAVAILABLE'

interface AppError {
  code: ErrorCode
  message: string
  retryable: boolean
  operationId?: string
}

type Result<T> = { ok: true; value: T } | { ok: false; error: AppError }

interface MutationContext {
  operationId: string
  expectedRevision: number
  workspaceEpoch: string
}

interface EntityRef {
  kind: 'event' | 'todo' | 'pending'
  id: string
  revision: number
}
```

`workspaceEpoch` 在主进程启动及恢复开始时更新，渲染层通过可信初始化接口获取；它用于识别旧界面请求，不代替权限检查，也不放进请求内容哈希。旧窗口、旧异步任务或恢复前打开的编辑框带旧 epoch 提交时返回 `STALE_PREVIEW`。创建类命令不要求目标 revision，但仍需 operationId；修改共享时间块等多实体命令携带所有被修改目标的 revision。

主进程依次执行来源验证、结构校验、epoch 验证、幂等查重、业务版本检查、业务事务与回执写入、持久化、广播和返回。幂等查重必须先于目标版本检查：成功提交后用原 revision 重试的相同请求应返回原结果，而非误报版本冲突。请求哈希由经过规范化的业务输入生成，排除瞬时窗口状态、密钥及日志字段。

持久化失败时不广播已保存成功，不提交新的依赖该结果的后续自动操作；界面展示未保存状态并保持操作 ID。对操作回执的内存保护只在当前进程有效；重启依赖实际磁盘库判断，不承诺无日志条件下恢复内存中丢失的事务。写入失败期间仍允许只读与导出当前内存状态的显式救援流程，后者须标明尚未持久化及可能不完整，不能伪装为常规成功备份。

查询、预览和授权意图同样验证权限。文件选择返回主进程持有的短期句柄或预览令牌，渲染层不能传任意路径来触发读写。恢复预览绑定归档哈希、业务数据修订与当前 epoch，预览后文件或本地业务变化时重新计算影响范围。

## 4. 迁移分组与失败恢复

迁移按以下逻辑组递进，实际 schema 数字由集成负责人按合入顺序唯一分配；逻辑组名称不等于已存在版本。每次发布只包含已实现且经过验收的迁移。

| 逻辑组 | 阶段 | 修改范围 | 必须先完成 | 回滚与校验 |
| --- | --- | --- | --- | --- |
| M1 写入基础 | S1 | 实体 revision、操作回执、持久化与生命周期元数据 | 恢复校验、落盘故障测试 | 旧 ID 和记录数不变；失败回到升级前快照 |
| M2 确认与来源 | S2 | 候选身份、pending 结果、业务变更记录、事项软删除及待办取消状态、旧邮件确认映射 | M1 | 已确认条目不重建；无来源旧条目可手动处理 |
| M3 隐私审计 | S2 | 发送快照、运行/尝试记录、本机授权策略、provider 配置修订 | M1 | 升级不生成默认授权；旧历史不自动发送 |
| M4 执行安排 | S3 | 周期、实例、例外、子任务、时间块关系 | M2 | 一次性旧事项不变；共享关联全部保留；无外键悬空 |
| M5 提醒中心 | S3 | 提醒任务、尝试、旧 fired_reminders 导入 | M4 | 不重发旧提醒；旧键无法解析时只归档，不猜测目标 |
| M6 备份归档 | S3 | 清单与备份目录登记、受控材料副本 | M2—M5 | 所有新业务表入清单；缺失材料有显式报告 |
| M7 Gmail | S4 | 认证/传输类型、协议专属可空字段、正文结构标记、REST 远端映射及检查点 | M1、M3 | 原 IMAP 身份、UID、状态不变；不自动改传输方式 |

迁移开始前停止业务服务并创建一致的恢复点；每个逻辑组的结构变化、数据回填和 schema 版本更新在单个数据库事务内完成，并在启动窗口前持久化。失败时不得继续启动部分可用界面写库。迁移期间文件复制在 staging 目录进行，先校验、后使业务记录引用，旧文件在整个升级成功前保留。

为每个支持的旧 schema 保存合成夹具，包含空库、已确认邮件、多待办共享日程、过期提醒、损坏引用和缺失附件。迁移后验证记录数、ID、引用、日期显示和已确认状态。真正损坏且无法无歧义修复的记录进入可导出的异常报告并阻止相关恢复，不采用 `INSERT OR REPLACE` 静默覆盖主键冲突。

完整业务备份的新格式应列出各业务表、字段结构版本及数量。旧 JSON 按已知版本校验其当时必需表后迁移，不能要求旧格式提供新清单，也不能因旧格式没有新表而当成有效空数据。未知未来版本不降级导入。schema 更新同时修改备份覆盖测试，新增业务表未被导出时测试必须失败。

## 5. 跨功能状态与交互边界

### 5.1 待确认处理与冲突

单次转换的状态路径为 `open → handled` 或 `open → dismissed`。编辑失败维持 open；提交成功保存目标引用。重复确认已有 handled 条目返回同一目标；目标后来被删除时显示原处理记录与目标已不可用，不自动创建第二个事项。需要重新创建时由用户发起全新操作并记录新来源关系。

批量处理按条目原子提交并返回每项结果，界面保留失败项的编辑内容和原因，成功项不会因整体重试再次执行。多个候选修改同一目标时按事务顺序执行版本检查，后一项冲突时要求重新预览，不能以最后写入获胜。

### 5.2 周期系列与执行安排

系列的 occurrence_key 表示原发生时刻，ordinal 表示在当前系列的规则位置；改动单次发生时间不改变这两个值。logical_instance_id 跨改期和系列拆分保持不变，F1 匹配与来源指向此逻辑身份及既有实体 ID，并携带系列、实例和例外的 revision。本次及以后修改生成新系列，原系列在分割点停止生成；所有已有历史和完成实例保留原 ID 和归属。

对未来实例的迁移先生成可审阅的新旧发生项映射，按新规则明确对应的未完成实例保持逻辑 ID 与实体 ID，更新当前系列键并保留旧键别名；其例外和来源继续依附同一逻辑身份。无法对应的例外、子任务或时间块在预览中要求用户选择保留为一次性事项或取消；存在未决定项时不能提交。取消项保留排除记录，共享时间块不自动删除，禁止只按数组下标配对后静默搬移。已完成项在新系列的对应位置保留排除映射，不能再生成一项未完成副本。

子任务默认继承父实例归属，不自动拥有独立周期规则。周期模板的子任务结构在生成实例时复制，已生成实例的编辑不改变模板；选择本次及以后修改模板时仅影响后续未完成实例，并展示已有子任务的影响。父任务完成不改变其他周期实例。

时间块共享同一 event ID 时，修改日程只执行一次并返回全部关联待办；移除某任务关系不删共享日程。取消父任务时展示是否取消其独占未来时间块，共享时间块保持并提示；自动操作不越过用户选择。截止提醒以待办自身 due_at 为准，不能根据最后一个时间块反推截止。

提醒准备按未来 90 天的触发时间窗口计算，而非简单地只展开未来 90 天内开始的日程。对提前提醒，把触发窗口转换为实例发生窗口，再有界展开，保证提前数天或更久的提醒不因发生时间超出窗口而遗漏。连续多年未启动只计算窗口内实例与已持久状态，不逐个补造所有历史记录。

### 5.3 稍后提醒与免打扰

稍后提醒生成明确的用户重排意图，生效时间保存为 UTC。原业务取消或完成会取消稍后任务；修改标题但不改变提醒规则时保留稍后时间。改期或截止变化后先显示影响，默认废止旧稍后安排并按新规则调度。已提交通知只保留历史，不能从操作系统撤回已显示消息来宣称取消成功。

免打扰期间新到期任务进入 deferred；界面可查看，桌面弹窗和桌宠气泡均暂缓。退出免打扰按合并摘要提示，并允许展开逐项查看；稍后时间仍处于免打扰内时继续延后，不绕过设置。恢复后不把已 acknowledged 的通知重新变为待触发。

## 6. 恢复隔离与隐私授权

恢复时先阻止新写入、取消可取消的外部请求并使旧 epoch 失效，等待已经接受的同步事务完成和落盘，再形成恢复前快照。尚未进入业务事务的迟到网络结果不允许提交。界面显示恢复进度并关闭旧编辑提交入口；结束后所有窗口重新加载 revision 和 epoch。

自动备份读取一致业务快照，之后的附件复制基于不可变受控材料清单，不长时间锁住整个界面。归档容量不足或文件消失时标记失败，保留上一份完整备份；仅在预览里显示“允许缺失材料”的手动导出才可生成明确的不完整归档，自动备份不能静默降低完整性。

恢复的 `analysis_runs`、快照和业务记录仅供查看历史，不构成发送授权。`privacy_grants`、入口自动发送偏好、短期 OAuth 会话及临时文件句柄不在业务归档中。恢复开始即撤销所有未执行的发送确认；恢复后第一次分析重新预览，即便本机仍保存相同模型服务配置也不能沿用旧 snapshot 的发送权限。

用户取消或撤销授权后，主进程停止未发出的重试、修复和备用请求，已发出的请求尽力取消并拒绝迟到结果写入。审计保留已发送这一事实、接收方及用量，不把取消操作写为从未发送。入口持久策略由用户显式启用，内容类别或接收方配置变更使授权范围失效，不能靠修改同名服务商继承权限。

快照准备器记录历史消息及摘要依赖的材料集合；旧历史缺少依赖信息，或无法证明其不含本次排除的材料时，保守排除该段历史和派生摘要，并在预览中告知可能缺少背景。这里保证的是请求组装不重新带入已排除数据，不依赖模型遵守“请忽略这些内容”的提示词来实现隔离。

用户删除原材料时，界面说明历史分析、变更记录和备份可能仍含派生内容。产品不承诺全局自动脱敏或删除远端模型日志；涉及本地关联数据清理时先展示实际范围并确认。诊断包默认排除材料、邮件正文、分析原文和业务 before/after 快照，用户可在导出预览中查看文件清单。

## 7. 客户端契约示例

本节用于冻结调用语义，具体类型文件在所属任务实现。操作 ID 在用户开始一次确定操作时生成，网络或保存重试复用；用户改变输入后创建新操作 ID。不得为每次按钮重试自动生成不同 ID 来绕过幂等。

```ts
interface ResolvePendingInput {
  context: MutationContext
  pendingId: string
  decision: 'create_event' | 'create_todo' | 'apply_change' | 'dismiss'
  editedCandidate: unknown // 由 decision 对应的运行时 schema 校验
  target?: EntityRef
}

interface ResolutionResult {
  pending: EntityRef
  targets: EntityRef[]
  changeIds: string[]
}

interface SearchHit {
  kind: 'event' | 'todo' | 'pending' | 'mail' | 'conversation'
  id: string
  title: string
  date?: string
  parentId?: string
}
```

`MutationContext.expectedRevision` 在 resolvePending 中对应 pending 的 revision；target.revision 对应被修改实体。对于创建事项，target 必须为空；dismiss 不允许携带待写入事项。主进程遇到额外危险字段拒绝而非忽略，不能让模型原始 payload 直接扩展数据库列。

搜索结果点击携带完整 SearchHit；页面加载后按 ID 定位，必要时切换日历日期或打开邮件详情。`parentId` 只用于辅助定位，后端仍检查实体真实归属。搜索错误显式返回，结果为空表示成功查询但无命中，两者使用不同界面状态。

## 9. 外部条件与阶段交付

Google 桌面客户端、授权屏幕及权限审核由项目维护者提供实际配置；开发可用本地替身完成大部分测试，但真实邮箱和公开分发结论必须以真实结果为准。凭据只通过应用或受保护的开发环境注入，不要求用户粘贴到文档。签名证书、发布地址与更新元数据属于 S6 条件，不能阻塞 S1—S5 的本地开发和自动化验收，也不能在条件缺失时宣称 F12 完成。

每个阶段的交付包含修改清单、schema 迁移记录、需求和 AC 用例对应结果、已执行命令、未覆盖场景及外部阻塞。全量测试数量可以增长或合理重组，不能仅以测试数量增加判断完成。性能阈值是目标，报告必须包含数据集与机器条件；模拟时钟及 UI 测试不替代 Windows 通知、托盘与睡眠行为验证。
