# 可讲述的工程失败案例

这些案例来自开发与回归验证，不属于真实模型效果实验。完整命令与原始日志位于 artifacts/acceptance/adc-rc1-20261002 各任务目录。

### 审批时间漂移

固定评测时间早于系统日期时，审批被系统时钟判定过期。定位到 runner 没有把案例 Clock 传入编排器，以及审批过期检查直接使用 Date。修复后注入统一 Clock，验证到期前、正好到期、到期后与跨系统年份。证据为 T01；系统时钟仍用于测量真实耗时，两类时间各司其职。

### 备份恢复与旧驱动竞态

业务表替换后旧执行者仍可能运行，使用相同 runId 的备份会放大风险。恢复前暂停领取、取消活跃任务并等待驱动完整 settle；超时则零替换，双重保存失败保持故障锁。恢复后的中断运行收尾并同步研究任务阶段。证据为 T02。故障锁需由明确恢复流程处理，不能为继续派发而静默释放。

### 多次审批丢失早先失败

一份计划先执行失败再执行成功时，只看当前驱动局部结果会把整体记成功。用稳定 operationId 汇总回执，观察记录补充没有回执的失败，重放不重复计数。四种成功/失败组合均有回归。证据为 T03，重复批准仍只产生两份业务回执。

### 业务保存与最终观察脱节

首次关键保存已有业务和回执，最后观察尚未落盘时返回成功会让证据缺失。工具成功返回前补最终观察保存，保存失败停止后续读取与规划；重试同 ID 只重放回执。业务已经应用的事实与保存错误分开记录。证据为 T04，不用 persist_error 推断没有发生写入。

### 不完整证据与跨实体综合

all_of 只验证引用是否存在会放过缺成员、跨实体或损坏清单。读取侧要求清单完整、唯一且同实体组，批次写入先验证全部成员，再事务写 evidence、claim、清单与 citation。逐表故障注入与重新打开数据库验证原子性。证据为 T09/T10。结构验证不能替代人工语义支持审阅。

### 检索候选过量

先读取全部 chunk 再截取 500 条会在高命中集合造成多余 IO 和内存。SQL 使用稳定排序与 LIMIT，并对冻结文档分批查询分配剩余额度，累计候选不超过 500。反例集合读取曾达到 1,610 条；回归直接检查 SQL 返回行数。证据为 T11，后续评分仍按实际候选执行。

### 实验目标受业务默认路由影响

把业务 ModelCompleter 直接交给评测可能使用默认供应商与备用模型，导致配置标签与实际请求不符。独立适配器按冻结目标构造唯一 provider，运行前验证 target hash 和凭据绑定；401/429 不切换或隐式重试。服务集成捕获实际 URL、model 和模板，真实请求不传 gold。证据为 T15，实际模型效果待付费实验验证。
